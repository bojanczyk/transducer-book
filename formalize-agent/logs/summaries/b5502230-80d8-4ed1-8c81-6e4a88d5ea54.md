## What I added

Working only inside `transducer-lean/`, and touching **no numbered result of the main text**:

* **Exercise `exer:decide-unambiguous` (unambiguity of an nfa is decidable) — now proved**, in the new file `RequestProject/Exercises/NFAUnambig.lean`. Following the author's solution, and following the way the book's other decidability exercises are formalised here, both halves are given: the criterion `ambiguous_iff_reach` (the automaton is ambiguous exactly when the product automaton — two copies reading the same input plus a bit recording whether the copies have parted — reaches a pair of accepting states with the bit set) and the resulting decision procedure `decidableUnambiguousNFA`. The automaton is Mathlib's `NFA`, whose transitions read one letter, which is the ε-free form the solution reduces to; runs are made explicit, and `mem_accepts_iff_exists_accRun` checks against Mathlib's semantics that the language is the set of inputs with an accepting run. The file also supplies what the last step takes for granted — reachability in a finite graph is decidable — and the instance genuinely computes: two `by decide` examples in the file confirm it on a concrete ambiguous automaton. The polynomial running time the solution claims is not formalised (the project has no model of running time), which is recorded in the docstring.
* **The first step of Exercise `exer:rational-injectivity-decidable` — proved**, in the new file `RequestProject/Exercises/RatInjective.lean`: a rational function is injective exactly when it has a rational left inverse (`rationalFun_injective_iff_exists_inverse`), obtained as the solution obtains it, by uniformising the inverse relation made total with a default output outside the range. This needed a closure property the project did not have, that **rational relations are closed under union** (`isRationalRel_union`), proved via the disjoint union of two nfas with output. The exercise as stated asks for a *decision procedure*; that second step is **not** formalised, because in this project such a statement is about codes of automata while the available uniformisation only asserts that a rational function exists, not that a code for one can be computed. The exercise therefore remains listed as *not formalised* in `EXERCISES.md`, with that explanation.

The other 23 unformalised exercises stay unformalised for the reasons already documented (statements about polynomial time or the number of states, growth rates of regular languages, Parikh images, Ehrenfeucht–Fraïssé games, or the string encoding of the configuration graph of a two-way transducer, which the project deliberately does not build). I re-read each justification against the sources and found them accurate; in particular `exer:2dfa-unary-output` and `exer:regular-outpus-of-exactly-linear-size` do rest on `lem:compute-configuration-graph`, and the recorded divergence about `exer:2dfa-complexity` stands.
